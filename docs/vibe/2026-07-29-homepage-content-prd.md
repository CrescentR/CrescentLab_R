# CrescentLab 首页内容 PRD

> 日期：2026-07-29  
> 状态：内容设计稿  
> 范围：公开首页 `/` 的 Hero、正在构建、实验观测台、项目、笔记与关于区块  
> 不在范围：本次不定义新的数据库字段、API、后台表单、页面视觉或动效实现

## 1. 背景

CrescentLab 的产品定位已经明确：它是一个自托管的个人技术实验室 CMS，用一个公开站点承载文章、项目与实验记录。

当前首页已经形成以下浏览顺序：

1. Hero：说明这是谁的站点、它在做什么。
2. 正在构建：展示当前投入精力的对象。
3. 实验观测台：展示构建过程中产生的问题、验证和失败。
4. 项目：展示已经形成稳定成果的系统。
5. 笔记：展示经过整理、可以被完整阅读和复用的结论。
6. 关于：说明站点身份和外部联系方式。

页面结构本身没有问题，主要问题是各区块的内容边界还不够清楚：

- “正在构建”目前只有名称和“进行中”，无法解释每个构建是什么、做到哪一步。
- “实验观测台”混入了阅读动态、开发进度和技术问题，部分内容没有体现“观察和验证”。
- “项目”与“正在构建”都在展示产品名称，但没有明确区分活跃工作与稳定成果。
- “笔记”已经读取真实文章，但首页文案没有明确说明它与实验记录的差别。

本 PRD 解决的是“每个区块到底应该写什么”，不是重做页面结构。

## 2. 产品目标

### 2.1 核心目标

让首次访问者在浏览首页后，能够准确回答四个问题：

1. 站点所有者现在正在做什么？
2. 这些工作基于哪些问题、实验和证据？
3. 哪些工作已经形成可以查看或使用的成果？
4. 有哪些完整文章可以继续阅读？

### 2.2 内容目标

- 各区块承担唯一且稳定的内容职责，不重复展示同一层信息。
- 首页不是简历、产品广告页或流水账，而是一份持续更新的公开研究档案。
- 每条内容优先提供事实、状态和结论，减少抽象口号。
- 项目、实验和文章之间能够建立阅读线索，但不要求所有内容强制互相关联。
- 首页保持精选摘要，不承担完整归档和复杂筛选。

### 2.3 非目标

- 不在本 PRD 中设计评论、订阅、读者账号或社区内容。
- 不把后台开发任务、提交记录和系统日志原样公开。
- 不为了填满版面制造虚构项目、虚构进度或虚构实验结果。
- 不要求一条内容同时出现在“正在构建”“实验观测台”“项目”和“笔记”四个区块。
- 不把首页做成所有内容的完整列表。

## 3. 目标读者与使用场景

| 读者 | 进入首页时想知道什么 | 首页应该提供什么 |
| --- | --- | --- |
| 第一次访问者 | 这是什么站点，值得继续看吗 | 一句话定位、当前关注方向、代表性内容 |
| 技术读者 | 遇到了什么真实问题，得出了什么结论 | 实验问题、观测结果、工程笔记 |
| 潜在使用者 | 有哪些东西已经可以使用或查看 | 项目状态、演示、仓库、适用对象 |
| 长期关注者 | 最近发生了什么变化 | 当前构建、最新观测、近期笔记 |
| 站点所有者 | 如何持续维护内容而不让区块混乱 | 明确的收录条件、字段模板和更新规则 |

## 4. 首页内容主线

首页采用以下叙事：

> 我正在做什么 → 我如何验证 → 我做成了什么 → 我沉淀了什么

对应关系如下：

| 区块 | 核心问题 | 内容时间尺度 | 内容确定性 | 主要动作 |
| --- | --- | --- | --- | --- |
| 正在构建 | 现在把精力放在哪里 | 天到数周 | 方向明确，结果未完成 | 查看当前进展 |
| 实验观测台 | 遇到了什么，验证后知道了什么 | 一次实验到数周 | 允许失败、变化和未决 | 查看观测详情 |
| 项目 | 哪些成果已经形成稳定对象 | 数月及以上 | 目标和边界相对稳定 | 查看项目、演示或仓库 |
| 笔记 | 哪些结论值得完整阅读 | 长期留存 | 已整理成可复用表达 | 阅读文章 |

### 4.1 四类内容的判断规则

同一条内容应该按照它当前最主要的用途归类：

- 重点是“最近正在推进到哪一步”时，放入“正在构建”。
- 重点是“提出问题、执行验证、记录结果”时，放入“实验观测台”。
- 重点是“介绍一个已经成形的系统及其使用方式”时，放入“项目”。
- 重点是“完整解释一个问题和结论”时，放入“笔记”。

内容之间可以转化，但不是自动升级流程。例如：

- 一个工具构想先作为观测记录，确认值得投入后进入“正在构建”。
- 一个活跃构建形成稳定边界、演示或仓库后进入“项目”。
- 一次实验产生可复用结论后，可以另写一篇“笔记”。
- 已经成为“项目”的对象仍可继续构建，但首页不应在两个区块使用完全相同的文案。

## 5. 全局内容原则

### 5.1 内容必须回答的问题

每个首页内容项至少回答以下三项中的两项：

- 这是什么？
- 为什么值得做或值得读？
- 当前得到了什么事实、进展或结果？

只有名称、标签或“进行中”的内容不能单独构成有效首页内容。

### 5.2 文案语气

- 使用第一人称研究记录或客观陈述，不使用企业宣传口吻。
- 标题写具体对象或明确判断，不使用“探索未来”“赋能创新”等空泛表达。
- 允许公开失败、放弃和限制，但必须说明原因或证据。
- 状态使用可验证描述，例如“完成登录闭环”“正在验证 PostgreSQL 恢复时序”，不用“持续优化中”。
- 日期优先使用明确日期；“今天”“本周”只用于确实会持续更新的动态内容。

### 5.3 摘要写法

推荐使用以下结构：

> 对象或问题 + 当前动作或结论 + 对读者的意义

示例结构：

> 为了解决【具体问题】，当前完成了【事实进展】；下一步将验证【明确事项】。

### 5.4 禁止内容

- 无法从项目、代码、记录或实际操作中证明的数字。
- 没有真实入口的“立即体验”“查看演示”等动作。
- 只描述情绪、不描述事实的开发感想。
- 把内部敏感信息、账号、密钥、部署地址和未公开数据写入首页。
- 用技术栈列表替代项目价值说明。

## 6. Hero 区块

### 6.1 内容职责

Hero 只负责建立身份、定位和阅读入口，不承担具体项目介绍。

访问者在首屏应知道：

1. 这是一个个人技术实验室。
2. 内容包括产品构建、开源实验和工程笔记。
3. 可以从当前构建或笔记继续浏览。

### 6.2 推荐内容结构

| 内容 | 要求 |
| --- | --- |
| 身份短句 | 说明站点性质，例如“独立研究 / 构建日志” |
| 主标题 | 保留站点名称 `CRESCENT LAB` |
| 核心主张 | 一句话表达工作方式，不罗列功能 |
| 站点说明 | 40–80 字，说明收录哪些内容、为什么公开 |
| 主入口 | 指向“正在构建” |
| 次入口 | 指向“笔记” |
| 状态读数 | 仅保留真实、低频变化的信息 |

### 6.3 当前内容判断

当前“构建想法。运行实验。发布留存成果。”与产品定位一致，可以保留。

当前站点说明已经覆盖“产品、开源实验、工程笔记和待证明想法”，不需要继续增加模块名称。后续重点是让下方区块兑现这段说明。

“模式 / 关注点 / 时区”可以作为实验室氛围信息，但不能替代真实内容。若“模式”和“关注点”长期不更新，应改为固定的站点事实，避免制造实时状态的错觉。

## 7. 正在构建

### 7.1 内容职责

“正在构建”展示当前真实投入时间、短期内会继续更新的工作。

它不是项目总目录，也不是愿望清单。进入本区块的对象必须已经开始行动，并且有当前阶段或近期进展可以说明。

### 7.2 收录条件

同时满足以下条件才展示：

- 已经开始设计、编码、制作或验证。
- 当前有清晰目标。
- 最近 30 天内有真实进展，或明确处于等待外部条件的状态。
- 能写出下一步要完成或验证的事项。

以下内容不展示：

- 只有名称、没有行动记录的想法。
- 已经停止但没有明确归档说明的对象。
- 已经稳定完成、当前没有持续构建内容的项目。
- 纯粹的日常任务，例如“修复若干问题”“整理代码”。

### 7.3 首页展示数量

- 推荐同时展示 2–4 个。
- 超过 4 个时，保留投入最高或最近更新的对象。
- 少于 2 个时允许留空或只展示 1 个，不用虚构内容补位。

### 7.4 每个构建项必须包含的内容

| 字段 | 首页用途 | 写作要求 |
| --- | --- | --- |
| 名称 | 识别对象 | 使用真实产品或项目名 |
| 一句话定义 | 解释这是什么 | 20–40 字，先写使用对象和用途 |
| 当前阶段 | 说明做到哪里 | 使用“原型、开发、验证、内测、暂停”等明确阶段 |
| 本轮目标 | 说明当前为什么投入 | 只写一个近期目标 |
| 最新进展 | 提供事实 | 写已经完成或已经观察到的内容 |
| 下一步 | 建立后续预期 | 写一个可检查的动作 |
| 更新时间 | 判断内容新鲜度 | 使用明确日期 |
| 入口 | 继续了解 | 只有真实详情、演示或仓库存在时显示 |

当前卡片空间有限时，首页至少显示：

> 名称 + 一句话定义 + 当前阶段 + 最新进展或下一步 + 更新时间

其余信息可以进入详情页或展开层。

### 7.5 卡片文案模板

```text
名称：
一句话定义：
当前阶段：
本轮目标：
最新进展：
下一步：
更新时间：
详情 / 演示 / 仓库：
```

### 7.6 当前内容缺口

当前 `QuickBox`、`NextVibe`、`Tarot Oracle`、`Crescent Blog` 只确认了名称、缩写和“进行中”状态。以下信息没有在现有首页内容文件中出现，不能直接补写：

| 构建项 | 必须补充的真实信息 |
| --- | --- |
| QuickBox | 使用对象、解决的问题、当前阶段、最新进展、下一步、公开入口 |
| NextVibe | 使用对象、解决的问题、当前阶段、最新进展、下一步、公开入口 |
| Tarot Oracle | 使用对象、解决的问题、当前阶段、最新进展、下一步、公开入口 |
| Crescent Blog | 与 CrescentLab 的关系、当前阶段、最新进展、下一步、公开入口 |

在这些信息补齐前，不应为四个名称编写产品功能或成果描述。

## 8. 实验观测台

### 8.1 内容职责

实验观测台记录尚未完全定型、但已经产生观察价值的内容。重点不是“我做了什么”，而是：

> 我想验证什么 → 我看到了什么 → 这个结果改变了什么判断

实验可以成功、失败、放弃或暂时未决。真实性比结果漂亮更重要。

### 8.2 收录内容

适合收录：

- 技术方案对比和验证。
- 原型或交互实验。
- 已确认原因的失败记录。
- 工具构想及其最小验证。
- 会影响后续设计的技术债。
- 阅读后改变项目判断的研究摘记。

不适合收录：

- 只有“本周做了什么”的进度播报。
- 没有个人判断的书摘或链接收藏。
- 已经整理成完整教程或长文的内容。
- 没有验证动作和观察结果的宽泛想法。

### 8.3 内容类型

现有观测台模型已经定义以下精确类型：

| `note_type` | 面向读者的内容含义 | 首页写作重点 |
| --- | --- | --- |
| `fragment` | 研究片段 | 一个值得保留、但还不能形成完整结论的观察 |
| `failure` | 失败记录 | 预期、实际结果、失败原因和避免重复的方法 |
| `idea` | 想法 | 问题来源、核心假设和最小验证方式 |
| `tool_idea` | 工具构想 | 使用场景、现有阻力和准备验证的能力 |
| `tech_debt` | 技术债 | 已知缺陷、现实影响、触发修复的条件 |

现有状态为：

| `status` | 内容含义 |
| --- | --- |
| `active` | 仍在验证或处理 |
| `resolved` | 已得到结论或完成处理 |
| `abandoned` | 明确停止，并保留停止原因 |

上述标识符保持与现有模型一致；中文仅作为内容解释，不代表本 PRD要求修改代码枚举。

### 8.4 每条观测必须包含的内容

| 内容 | 要求 |
| --- | --- |
| 标题 | 直接写问题或观察，不写泛化栏目名 |
| 类型 | 使用现有 `note_type` |
| 状态 | 使用现有 `status` |
| 背景 | 为什么出现这个问题 |
| 假设或预期 | 原本认为会发生什么 |
| 行动 | 实际做了什么验证 |
| 观察 | 发生了什么，有什么证据 |
| 当前结论 | 目前可以确认什么，仍不能确认什么 |
| 下一步 | 仅在 `active` 时需要 |
| 标签 | 1–4 个足以帮助识别主题的标签 |
| 日期 | 创建日期或最近更新日期 |
| 关联对象 | 如确实相关，可指向某个构建或项目 |

首页卡片摘要建议使用：

> 问题 + 关键观察 + 当前结论

详情内容再展开背景、行动和证据。

### 8.5 首页展示规则

- 首页精选 3 条，保证用户能完整读完，不在首页增加筛选器。
- 优先展示能体现不同结果的记录，例如一条进行中、一条已解决、一条已放弃或失败。
- 同一项目的多条连续记录只保留最有信息量的一条。
- 纯时间排序不能代替内容选择；首页应优先展示对外部读者有判断价值的记录。

### 8.6 当前三条内容的调整建议

| 当前条目 | 判断 | 调整方向 |
| --- | --- | --- |
| 最近阅读 | 有条件保留 | 增加“这次阅读回答了什么问题、改变了什么设计判断”，否则只是一条阅读动态 |
| 本周构建 | 不适合作为当前观测文案 | 若只是开发进度，应并入“正在构建”；若确实做了方案验证，应改写为问题、验证和结果 |
| 待验证问题 | 符合观测台方向 | 补充验证方式、当前证据和完成判断标准 |

## 9. 项目

### 9.1 内容职责

“项目”展示已经形成稳定名称、明确用途和可持续维护边界的成果。

项目可以仍在迭代，但访客必须已经能够理解它是什么。最好具备详情、演示、仓库或可核对的成果之一。

### 9.2 收录条件

满足以下条件中的大部分：

- 有稳定名称和一句话定位。
- 有明确使用对象或使用场景。
- 已经形成可描述的核心能力。
- 有演示、仓库、截图、文档或真实使用结果。
- 后续迭代不会推翻它的基本定位。

只有想法、一次性脚本、未开始的计划不进入项目区。

### 9.3 首页展示数量

- 推荐精选 3 个，保持当前页面结构。
- 排序首先考虑代表性，其次考虑最近更新。
- 已归档项目可以保留在完整项目列表，不占首页精选位置。

### 9.4 项目卡片内容

现有项目模型已经支持 `name`、`tagline`、`description`、`cover_url`、`repo_url`、`demo_url`、`status`、`tech_stack`、`published_at` 和 `updated_at`。

首页卡片建议投影为：

| 内容 | 对应现有信息 | 写作要求 |
| --- | --- | --- |
| 项目名 | `name` | 使用稳定正式名称 |
| 一句话定位 | `tagline` | 写给谁、解决什么问题 |
| 项目摘要 | `description` | 说明为什么做、现在能做什么 |
| 发布状态 | `status` | 公开端只展示已发布项目 |
| 技术标签 | `tech_stack` | 最多显示 3–5 个，不替代价值描述 |
| 更新时间 | `updated_at` 或 `published_at` | 让读者判断维护状态 |
| 演示入口 | `demo_url` | 仅在真实可访问时显示 |
| 仓库入口 | `repo_url` | 仅在真实可访问时显示 |
| 封面 | `cover_url` | 展示真实界面、结构图或结果，不使用无关装饰图 |

### 9.5 项目详情应写什么

现有 `content_html` 可以承载项目完整叙事，不要求为了以下章节立即新增字段：

1. 项目是什么。
2. 为什么要做。
3. 为谁解决什么问题。
4. 当前已经具备什么能力。
5. 关键设计或技术取舍。
6. 当前限制和明确不做的事情。
7. 重要里程碑或版本变化。
8. 演示、仓库和文档入口。
9. 相关实验与相关文章。

### 9.6 当前内容判断

当前 `CrescentLab`、`Prompt Foundry` 和 `Atelier Index` 已经具有名称、定位和摘要，内容形态比“正在构建”完整。

但当前首页使用的是 `mockData.ts`，项目点击后只显示三个短章节名称；现有后端项目接口仅注册在管理端，公开项目读取和正式详情入口尚未形成。这是后续实现依赖，不应在当前页面文案中伪装成已存在的公开能力。

## 10. 笔记

### 10.1 内容职责

“笔记”展示已经整理成完整文章、能够独立阅读和长期引用的内容。

它与实验观测台的差别是：

- 实验观测台保留过程、不确定性和局部结果。
- 笔记提供完整上下文、清晰论点和可复用结论。

### 10.2 适合发布为笔记的内容

- 工程问题的分析与解决过程。
- 一个项目的架构、设计取舍或复盘。
- 多次实验后形成的总结。
- 能改变实践方式的阅读笔记。
- 对工具、工作流或信息架构的完整方法说明。

以下内容不应直接作为完整笔记：

- 只有一句判断的碎片。
- 没有个人分析的大段摘录。
- 单纯复制提交记录的开发周报。
- 没有上下文和验证结果的教程步骤。

### 10.3 首页文章卡片内容

现有公开文章列表支持标题、slug、摘要、封面、置顶状态、阅读时间、发布时间和更新时间等信息。

首页每条笔记应显示：

| 内容 | 写作要求 |
| --- | --- |
| 标题 | 写出具体问题、方法或结论 |
| 摘要 | 60–120 字，说明讨论对象和读者能得到什么 |
| 分类 | 使用真实内容分类，不用发布状态代替分类 |
| 发布日期 | 优先显示 `published_at` |
| 阅读时间 | 使用现有 `reading_time_minutes` |
| 封面 | 可选；应与文章内容有关 |
| 关联项目 | 仅在关系明确时显示 |
| 阅读入口 | 指向真实文章详情 `/articles/{slug}` |

### 10.4 标题规范

推荐：

- “PostgreSQL 恢复阶段为什么会拒绝连接”
- “把项目进度与实验记录分开的三个判断标准”
- “一次首页信息架构重构前需要固定哪些边界”

不推荐：

- “一些思考”
- “最近的感悟”
- “技术分享”
- “持续更新中”

### 10.5 摘要规范

摘要不重复标题，也不使用“本文将介绍……”开场。建议写：

> 出现了什么问题 + 文章给出的核心判断 + 适用边界

### 10.6 首页展示规则

- 推荐展示 6 篇：置顶文章优先，其余按发布时间倒序。
- 首页不展示草稿、定时内容和归档内容。
- 同一主题连续发布多篇时，摘要必须说明各自差异。
- 完整归档、分类筛选和搜索应放在文章列表页，不堆到首页。

当前实现请求 10 篇文章；已有阶段规划写明首页最多展示 6 篇。本 PRD采用 6 篇作为内容密度目标，具体代码调整需要另行实施和验证。

## 11. 关于与页脚

### 11.1 内容职责

关于区块回答“谁在维护这个站点、为什么持续记录、如何联系”，不重复 Hero 的产品介绍。

### 11.2 应包含的内容

- 一句身份说明。
- 一句记录原则或长期方向。
- 真实 GitHub 地址。
- 真实联系方式或联系页。
- 可选：站点源码、许可证或部署说明入口。

### 11.3 当前内容缺口

当前页脚显示 `GitHub` 和“联系方式”，但只是文本，没有真实链接。正式公开前必须补充确切地址；没有地址时应隐藏入口，而不是展示不可点击的联系项。

## 12. 跨区块关联

### 12.1 关联目的

关联的目标是帮助读者继续阅读，不是为了制造复杂内容关系。

推荐的关联方向：

- 正在构建 → 对应项目详情或最近一条观测。
- 实验观测 → 关联构建、项目或最终笔记。
- 项目 → 关联关键实验和相关文章。
- 笔记 → 关联相关项目。

### 12.2 关联规则

- 一条内容最多展示 1 个主要关联入口。
- 没有明确关系时不展示。
- 链接文案写目标内容名称，不使用“了解更多”。
- 关联对象未公开时，不在公开端生成入口。

## 13. 内容更新机制

### 13.1 建议更新频率

| 区块 | 检查频率 | 更新触发条件 |
| --- | --- | --- |
| Hero | 每季度或定位变化时 | 站点方向发生变化 |
| 正在构建 | 每周检查 | 阶段、进展、下一步发生变化 |
| 实验观测台 | 每次得到新观察时 | 产生证据、结论或停止原因 |
| 项目 | 每次重要版本后 | 核心能力、入口或边界变化 |
| 笔记 | 发布时 | 新文章正式发布 |
| 关于 | 每半年检查 | 身份、链接或联系方式变化 |

### 13.2 过期处理

- 正在构建超过 30 天没有进展时，必须更新状态、说明暂停或移出首页。
- 实验停止时，将状态明确更新为 `resolved` 或 `abandoned`，不能长期停留在 `active`。
- 项目入口失效时先移除入口，再决定是否归档项目。
- 文章内容失效时在正文补充修订说明，不静默修改原结论。

## 15. 实施优先级

### P0：内容边界成立

- 每个区块符合本 PRD 的收录条件。
- “正在构建”不再只有名称和状态。
- “实验观测台”每条内容都有问题与观察。
- “项目”不再与“正在构建”重复同一层信息。
- “笔记”使用真实文章标题、摘要和入口。

### P1：真实数据与详情闭环

- 项目区读取已发布项目并进入真实详情。
- 观测台有明确的公开读取边界和详情入口。
- 构建项可以关联项目或观测。
- 文章展示真实分类和关联项目。

P1 涉及接口与页面实现，需要另行拆分开发需求；本 PRD 不直接规定实现方式。

### P2：归档与发现

- 独立项目列表或归档页。
- 独立实验观测归档。
- 文章分类、筛选与搜索。

只有首页真实内容稳定后再考虑 P2，避免先建设空归档。

### 16.2 正在构建验收
